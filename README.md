# Reconciliation deployment

1. Run `F_STANDARD_SELECTION.sql` **once** to create the shared R18/R25 source and parsed streams for both DDAY and RHS. Its DROP statements recreate the parsed topics; do not rerun it between batches. The shared input topics are `R18.F_STANDARD_SELECTION` and `R25.F_STANDARD_SELECTION`.
2. Run `DDAY/R18_FBNK_EB_C005.sql` and `DDAY/R25_FBNK_EB_C005.sql` for DDAY. Run `DDAY/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `DDAY/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.
3. For each RHS batch under `RHS/RHS1/` through `RHS/RHS4/`, run its two stream SQL files (`R18_FBNK_EB_C005.sql` and `R25_FBNK_EB_C005.sql`), then its own `report.sql` **before** deploying the matching connectors. Each batch has separate Oracle sink tables, diff table, view and comparison procedure, named with its batch prefix (`RHS1` … `RHS4`). For example, RHS1 sinks into `CONFLUENT.RHS1_R18_FBNK_EB_C005_EXPLODED` and `CONFLUENT.RHS1_R25_FBNK_EB_C005_EXPLODED`; its report uses `CONFLUENT.RHS1_R18_R25_FBNK_EB_C005_DIFF` and `CONFLUENT.P_COMPARE_RHS1_R18_R25_FBNK_EB_C005`. There is no shared `RHS/report.sql`. Once that batch's sinks have caught up, call its comparison procedure again; do not rerun the whole report script, because it drops and recreates that batch's tables. Stop a batch's connectors before recreating its tables. Reports for other batches are not dropped or overwritten.
   - `RHS/RHS1/report.sql`
   - `RHS/RHS2/report.sql`
   - `RHS/RHS3/report.sql`
   - `RHS/RHS4/report.sql`

   When migrating existing deployments, stop the affected RHS connectors before changing `table.name.format`. Their identities and input topics are unchanged, so their committed offsets are retained: changing the destination alone does not backfill the new empty batch tables. Verify that the full required exploded input is still retained, then reset the stopped sink connector's offsets to the required starting position through the Kafka Connect version's supported offset-management interface, or deploy a fresh connector identity configured to start at the required earliest offsets. If retained input is incomplete, republish/recompute the complete required batch before consuming it. Resume only after the new tables exist; verify expected RECID/asset coverage on both sides as well as sink completion before comparing. Do not blindly copy old shared tables, which may contain mixed batches. Existing shared RHS tables and report objects are not migrated or deleted by the new scripts; retain them until any needed historical results have been archived.

All DDAY/RHS ksqlDB pipelines use schema ID `6226` for `EB_CONTRACT_BALANCES` in `PARSE_T24_RECORD`. Each derived stream projects `ROWKEY` to preserve the Kafka message key required by ksqlDB. `ROWKEY` is the message key, not a column in the Oracle sink tables; the connectors use `RECID, ASSET_TYPE` from the record value as their upsert primary key. Confirm the hard-coded `20261003` used by `EXPLODE_ASSET_BALANCES` matches the intended reconciliation date.

The report scripts DROP existing Oracle objects without an existence check; on first deployment, handle the expected missing-object errors or run only the CREATE section. Their final procedure invocation runs before the sinks have populated newly created tables. Each report compares only `OPEN_BAL`, `DR_MVT`, `CR_MVT`, `CLOSE_BAL` and row presence, not metadata fields.

All five reports use `/*+ PARALLEL(8) */` for the comparison SELECT and the result count/detail queries.

The connectors contain database credentials as requested: restrict access to these files and rotate the password if it is exposed. The Oracle wallet must exist at the configured path on every Kafka Connect worker.

## QUICKCHECK and DDAY cutover

Every DDAY/RHS1-RHS4 stream script creates a side-specific `FBNK_EB_C005_QUICKCHECK` stream/topic. It preserves `ROWKEY`, `RECID`, `OP_TYPE`, parsed source timestamps and `XMLRECORD`, selecting exactly `XMLRECORD = '' OR XMLRECORD IS NULL`. It is a diagnostic branch, not a filter on the main parsed/balance pipeline, and has no Oracle sink connector. For example, inspect `DDAY_R18_FBNK_EB_C005_QUICKCHECK` or `RHS1_R25_FBNK_EB_C005_QUICKCHECK` in ksqlDB.

The DDAY cutover changes source topics to `DDAY_R18.FBNK_EB_C005` and `DDAY_R25.FBNK_EB_C005`, as well as all derived stream/topic names, connector names and Oracle object names. Configure the upstream publishers to supply these source topics, stop the old connectors, deploy the new stream/report scripts and DDAY connectors, then wait for the new sinks to catch up before comparing. Existing deployed objects, stored rows and connector offsets are not automatically renamed or migrated. Do not delete old deployed data until the new reconciliation is verified; replay requires the needed records to remain available in the new source topics.

## Deployment verification boundaries

- Before rerunning stream scripts, identify and terminate their existing persistent ksqlDB queries using the target version's supported lifecycle commands. `DROP ... IF EXISTS` does not terminate running queries. Do not drop the shared schema streams while any group depends on them.
- Supply complete, controlled reconciliation snapshots or rebuild the sinks externally. The baseline pipeline upserts emitted assets but does not delete a stored asset when a later record removes it or produces no rows; forwarding `OP_TYPE` is not an Oracle delete operation. QUICKCHECK does not quarantine records from the main parser.
- Verify stable Kafka keys/partition ordering for updates to the same `(RECID, ASSET_TYPE)`. JDBC upsert does not reject an older `COMMIT_TS`; multiple tasks do not establish global source-time ordering.
- Verify expected record/asset coverage and equivalent business cutoffs for R18/R25, not just zero connector lag. The report's exclusive lock protects its diff table, not synchronization of the two upstream sinks. Run the comparison procedure from a dedicated reporting session because its COMMIT also commits other work in that session.
- Validate actual UDF/Avro output types, registry schemas, timestamp/time-zone handling and Oracle field widths. Balances remain `NUMBER(38,4)` as in the baseline: more than four fractional digits are rounded, and more than 34 integer digits cannot fit. SQLite smoke does not verify this financial precision boundary.
- Restrict worker logs and DLQ access: `errors.log.include.messages=true` can expose record data including CUSTOMER. With `errors.tolerance=none`, task errors must be investigated; a configured DLQ is not proof that processing continues.
- Verify execution plans and capacity on the target Oracle environment. `PARALLEL(8)` is a hint, not a guarantee of actual degree, and concurrently running reports can multiply resource demand.

## Initial-commit logic audit

Baseline: `cb70419eb8e20036a53ef7ee14ae3f1f4bf86c72`. All ten business stream scripts and connector configurations are equivalent after normalizing group/side names; all five reports are equivalent after normalizing group names. R18/R25 source/schema-parser streams are symmetric and match the baseline. The five business stream statements per side match the baseline except added `CUSTOMER`, environment-specific schema ID and the explicitly accepted date change.

- Preserved: timestamp parsing, message keys, balance UDF argument order, `CURR_ASSET_TYPE IS NOT NULL`, all balance projections, `(RECID, ASSET_TYPE)` upsert keys, null-safe comparisons of the four balance fields, full outer join, and missing-record versus missing-asset classification. Metadata does not trigger differences.
- Informational additions: `CUSTOMER` and four `DIFF_*` amounts (`R25 - R18`). A delta remains NULL when either operand is NULL; missing data is not treated as zero.
- Approved differences: reconciliation date `20260530` becomes `20261003`; the historical `COMPARE_RUN_ID` report becomes a per-group snapshot using exclusive-lock DELETE/INSERT with savepoint rollback. - Deployment differences: group-specific namespaces and separate reports, shared schema-parser setup, connector `tasks.max` 10 becomes 8, and a changed Schema Registry endpoint. These are not balance comparison rules. The local schema contains all eight fields read by the pipelines; the live registry schema and external UDF implementations still require environment verification.
