# Reconciliation deployment

1. Run `F_STANDARD_SELECTION.sql` **once** to create the shared R18/R25 source and parsed streams for both DDAY and RHS1. Its DROP statements recreate the parsed topics; do not rerun it between groups. The shared input topics are `R18.F_STANDARD_SELECTION` and `R25.F_STANDARD_SELECTION`.
2. Run `DDAY/R18_FBNK_EB_C005.sql` and `DDAY/R25_FBNK_EB_C005.sql` for DDAY. Run `DDAY/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `DDAY/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.
3. Run `RHS1/R18_FBNK_EB_C005.sql` and `RHS1/R25_FBNK_EB_C005.sql` for RHS1. Run `RHS1/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `RHS1/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.

`DDAY/` and `RHS1/` are sibling groups with independent Oracle tables, latest views, DIFF views/tables and comparison procedures. Moving RHS1 changes repository paths only; stream/topic/connector names, Oracle object names and committed offsets remain unchanged. Do not recreate deployed objects just because files moved. Removing group files from the repository does not terminate deployed queries/connectors or delete external resources.

All DDAY/RHS1 ksqlDB pipelines use schema ID `6226` for `EB_CONTRACT_BALANCES` in `PARSE_T24_RECORD`. Each derived stream projects `ROWKEY` to preserve the Kafka message key required by ksqlDB. `ROWKEY` is the message key, not a column in the Oracle sink tables; EXPLODED connectors use `RECID, ASSET_TYPE` and DEBUG connectors use `RECID` from the record value as their upsert primary key. Confirm the hard-coded `20261003` used by `EXPLODE_ASSET_BALANCES` matches the intended reconciliation date.

The report scripts DROP existing Oracle objects without an existence check; on first deployment, handle the expected missing-object errors or run only the CREATE section. Their final procedure invocation runs before the sinks have populated newly created tables. Each report compares only `OPEN_BAL`, `DR_MVT`, `CR_MVT`, `CLOSE_BAL` and row presence, not metadata fields.

Both reports retain `/*+ PARALLEL(8) */` for the comparison SELECT and inspection queries; latest-view definitions do not force parallelism. REPORT contains the procedure invocation, followed by COUNT and INSPECT. Both diagnostic sections order objects as raw EXPLODED (R18, R25), latest EXPLODED views (R18, R25), DEBUG (R18, R25), then DIFF. Raw EXPLODED/DEBUG COUNT queries retain `INDEX_FFS(t)`; latest-view and DIFF queries do not force an index. COUNT queries are unfiltered and occupy two lines. INSPECT queries occupy three lines and end with `WHERE RECID = '';`: replace the empty string with the intended RECID; Oracle treats the unchanged empty string as NULL, so it matches no rows. No inspection query includes ORDER BY. Standalone `/` delimiters remain omitted for DBeaver. Execute each complete `CREATE ... PROCEDURE ... END;` or `BEGIN ... END;` block as one statement/selection, not as separate internal statements; SQL*Plus/SQLcl require a `/` after each complete PL/SQL block. Oracle decides whether to honor hints; verify actual plans in the target environment. Latest views use the compact `MAX + JOIN` form; DIFF projections and procedure INSERT/SELECT blocks retain one projection column per line. Independent statements are separated by one blank line. All SQL section headings use the stream convention: a title enclosed by two `-- ============================================================` lines, with one blank line before and after the heading block except at file start. KSQL preambles consistently use SET, then the run-once note, then section headings. Within each consecutive group, AS aliases, column types and WITH property assignments align after the longest expression/name plus one space, following the source streams. DEBUG section titles contain only the stream name, like the other streams. RTRIM CASE expressions remain vertically aligned; logical blocks use four-space indentation with aligned expression continuations.

All SQL JOIN predicates keep the joined alias, ON and AND on the same line, including the closing `) m` of latest-view subqueries. Projection lists, section headings and other statement layouts retain the shared conventions above.

The connectors contain database credentials as requested: restrict access to these files and rotate the password if it is exposed. The Oracle wallet must exist at the configured path on every Kafka Connect worker.

## Latest EXP reconciliation baseline

The latest-view definitions and their consumers are owned by each group's `report.sql`, for example [RHS1/report.sql](RHS1/report.sql). "Latest" means every stored EXPLODED row at the greatest `COMMIT_TS` for its `RECID`, not one row per RECID and not the greatest timestamp separately for each asset. Assets tied at that timestamp must all remain available to reconciliation. R18 and R25 determine their own latest timestamps; equality between the two sides' timestamps is not a comparison rule.

The reconciliation path is EXPLODED sink tables -> `V_<group>_<side>_FBNK_EB_C005_EXPLODED` -> `V_<group>_R18_R25_FBNK_EB_C005_DIFF` -> comparison procedure -> DIFF snapshot table. Missing-record classification must use the same latest dataset as the full outer join, not raw EXPLODED history. Raw COUNT/INSPECT remain available for diagnosing excluded older assets; latest COUNT/INSPECT show the report inputs. A latest view is live, not a materialized snapshot; the DIFF table changes only when its comparison procedure runs.

For an existing populated deployment, apply only the missing `CREATE INDEX` statements and the `CREATE OR REPLACE VIEW` statements for both latest views and the DIFF view from that group's report. Do not run DROP TABLE, CREATE TABLE or CTAS during this view-only cutover. Existing same-named indexes must be verified as nonunique `(RECID, COMMIT_TS)`, not blindly recreated. Validate dependent objects and grants, then rerun the comparison procedure after both sides have reached the intended cutoff. Oracle DDL commits independently; archive the old definitions/report and schedule the cutover without concurrent reporting.

Release prerequisites:

- `COMMIT_TS` is guaranteed non-null by the source contract. Keep the existing sink schema and MAX-equality semantics; do not add a fallback timestamp or a redundant NULL filter.
- Supply complete emitted asset snapshots per RECID. The sink upserts `(RECID, ASSET_TYPE)` and does not retain all historical versions. A newer emitted batch hides older stored assets, but a version emitting no EXPLODED rows or a delete cannot advance the view's maximum. A late upsert can overwrite a newer row; the view cannot recover it.
- Complete both R18/R25 asset batches before comparing. One row arriving at a newer timestamp immediately advances the live view and temporarily hides the remaining older rows. Zero lag alone does not prove asset coverage, ordering, or equivalent business cutoffs; the report lock does not freeze either sink.
- Confirm `COMMIT_TS` identifies versions at the pipeline's effective timestamp precision, including Oracle `TIMESTAMP(3)`. Distinct versions sharing the stored timestamp are indistinguishable and all matching assets are retained.
- Validate Oracle object compilation/privileges, grants for the new views, index definitions/statistics, actual plans and report capacity on the target environment. View consumers need SELECT permission on the new views; existing table grants are not automatically view grants.
- Validate registry schema `6226`, external parser/balance UDFs, Avro types, timestamp/time-zone handling and the intended `20261003` business cutoff. Local SQL adaptation cannot establish these runtime contracts.
- Review the existing embedded credentials, disabled database TLS DN matching, HTTP Schema Registry and message-inclusive error logging against the target environment's security policy. These settings are not validated or hardened by the latest-view cutover.

Local verification of this baseline: actual report DDL/view queries and procedure DELETE/INSERT SQL were executed in isolated in-memory SQLite databases for DDAY and RHS1. Fixtures covered multiple assets tied at latest, stale-asset exclusion, independent side timestamps, latest-based missing-record/asset classification on both sides, each balance mismatch, NULL versus zero, NULL equality, metadata-only differences, delta direction, repeated/empty snapshot refresh, and raw/latest diagnostics and teardown. The raw baseline produced a stale-asset mismatch that the latest inputs removed. Group/side-normalized stream/report consistency and connector JSON/topic/table/key contracts were also checked; independent source reviews found no new defect. SQLite adaptations covered Oracle DECODE, NULL concatenation, CREATE VIEW and index syntax, not Oracle compilation, PL/SQL execution/locks/rollback, financial precision, live ksqlDB/UDF/Avro or Kafka Connect. No Oracle SQL client or accessible local container runtime was available, so target-runtime and security release gates remain open.

## QUICKCHECK and DDAY cutover

Every DDAY/RHS1 stream script creates a side-specific `FBNK_EB_C005_QUICKCHECK` stream/topic. It retains `ROWKEY` and all five value fields declared by the first source stream (`RECID`, `OP_TYPE`, `OP_TS`, `CURRENT_TS`, `XMLRECORD`), with no value-field additions, renames or transformations, selecting exactly `XMLRECORD = '' OR XMLRECORD IS NULL`. The timestamp fields remain their original strings; fields present in the Kafka value but not declared in the source stream are not included. It is a diagnostic branch, not a filter on the main parsed/balance pipeline, and has no Oracle sink connector. For example, inspect `DDAY_R18_FBNK_EB_C005_QUICKCHECK` or `RHS1_R25_FBNK_EB_C005_QUICKCHECK` in ksqlDB. Stop the existing QUICKCHECK query before rebuilding the branch; its value schema changes from `COMMIT_TS`/`REPLICAT_TS` timestamps to `OP_TS`/`CURRENT_TS` strings, so account for the existing topic's Schema Registry compatibility policy during deployment.

The DDAY cutover changes source topics to `DDAY_R18.FBNK_EB_C005` and `DDAY_R25.FBNK_EB_C005`, as well as all derived stream/topic names, connector names and Oracle object names. Configure the upstream publishers to supply these source topics, stop the old connectors, deploy the new stream/report scripts and DDAY connectors, then wait for the new sinks to catch up before comparing. Existing deployed objects, stored rows and connector offsets are not automatically renamed or migrated. Do not delete old deployed data until the new reconciliation is verified; replay requires the needed records to remain available in the new source topics.

## Parsed DEBUG sinks

All four DDAY/RHS1 R18/R25 stream scripts create a `_DEBUG` branch directly from their `_PARSED` stream. For example, `RHS1_R18_FBNK_EB_C005_DEBUG` publishes to `RHS1_R18.FBNK_EB_C005_DEBUG` and sinks into `CONFLUENT.RHS1_R18_FBNK_EB_C005_DEBUG`. The balance/report pipelines are unchanged.

The DEBUG value contains `RECID`, `OP_TYPE`, `COMMIT_TS`, `REPLICAT_TS` and all eight fields declared in `schema.json`: `APPLICATION`, `CUSTOMER`, `DATE_LAST_UPDATE`, `CURR_ASSET_TYPE`, `OPEN_BALANCE`, `DEBIT_MVMT`, `CREDIT_MVMT`, `TYPE_SYSDATE`. Every parsed field has an explicit alias and remains an unmodified string, including multivalue/subvalue separators, leading zeros and decimal digits. Oracle stores all eight parsed fields as `CLOB`, preserving values longer than 4000 characters without truncation. RECID remains VARCHAR2(255), OP_TYPE remains VARCHAR2(16), and timestamps remain TIMESTAMP(3). The tables contain only these twelve value columns, starting with RECID; there are no Kafka coordinate columns. `ROWKEY` remains the Kafka key, not an Oracle value column. Original XML and unparsed timestamp strings are not present in PARSED and are not added to DEBUG.

DEBUG deliberately has no `CURR_ASSET_TYPE IS NOT NULL` filter: it includes parsed records with missing assets or NULL DATA. It cannot capture records that fail before PARSED emits them, nor fields excluded by the live parser schema. Confirm registry schema 6226 matches the local eight-field schema; parser/UDF behavior remains an external prerequisite.

Each directory (`DDAY/`, `RHS1/`) defines both R18/R25 DEBUG tables in its normal `report.sql`, alongside EXPLODED. The script includes DROP TABLE ... CASCADE CONSTRAINTS PURGE, CREATE TABLE with RECID NOT NULL and PRIMARY KEY (RECID), and the same COUNT/SELECT inspection queries as EXPLODED. The primary key supplies the RECID lookup index. Rerunning report.sql recreates both DEBUG and EXPLODED sink tables; there is no separate debug.sql deployment step.

Each DEBUG connector matches its corresponding EXPLODED connector exactly except its name, input topic and destination table use DEBUG, and `pk.fields=RECID` instead of `RECID, ASSET_TYPE`. This includes `insert.mode=upsert`, `pk.mode=record_value`, `auto.create=false`, `auto.evolve=false` and the shared side-specific `<group>_<side>.SINK_ERROR` DLQ. DEBUG tables retain one row per RECID: the last applied event overwrites the previous value; they do not retain event history or reject older COMMIT_TS values. Replay of the same value does not add rows. NULL RECID fails the primary-key contract. Provision and verify the explicit report.sql table schemas before starting either sink type; connectors must not create inferred tables when provisioning is missing.

Deploy DEBUG through the same lifecycle as EXPLODED: stop the affected connectors and persistent stream queries before rebuilding, run the group's two stream scripts and report.sql, then deploy/resume the matching EXPLODED and DEBUG connectors. Recreating sink tables does not reset committed connector offsets; replay retained input using the supported offset-management interface or fresh connector identities to repopulate both sinks. Earliest cannot restore expired/compacted records. After the sinks catch up, call the comparison procedure again instead of rerunning report.sql. Apply the same backup/data-loss precautions to both sink types.

Restrict topic/table/DLQ access because these records contain customer and balance data.

Local verification: all four DEBUG connectors matched their corresponding EXPLODED configuration after changing only DEBUG identity fields and the RECID key. SQLite-adapted upsert smoke verified replacement of a RECID value, replay without duplicate rows, NULL-key rejection and unchanged twelve-column layouts. Integrated report lifecycle smoke verified both DEBUG tables in both reports: DROP/CREATE clears old rows, COUNT/SELECT inspection queries execute, and the schemas and existing report logic remain unchanged. This is not live ksqlDB/UDF, Avro, Kafka Connect or Oracle validation, and SQLite does not enforce Oracle VARCHAR2 width semantics. The DEBUG CLOB smoke preserved strings longer than 100 KB and NULL values across all eight parsed fields, with RECID upsert/replay unchanged. Before rollout, verify actual schema/string types, TIMESTAMP mapping and Oracle JDBC CLOB binding/upsert with large values using the deployed versions. No Oracle or ksqlDB SQL client was available locally.

## JDBC sink DLQ policy

Connector configs own the `<group>_<side>.SINK_ERROR` destination; EXPLODED and DEBUG share the same side-specific DLQ. Context headers identify the original topic/partition/offset, connector/task, failure stage and exception details. The DLQ retains the failed original key/value bytes, not an Oracle error table or a new business-record schema.

The baseline keeps `errors.tolerance=none`: failures are not silently skipped so reconciliation can continue with missing records. In upstream Kafka Connect error handling, a record may be reported to the DLQ before the tolerance check fails the task; a failed task therefore does not prove the DLQ is empty, and a configured DLQ does not guarantee delivery or continued processing. Validate the installed Kafka Connect/JDBC versions and actual task/DLQ state before relying on this behavior.

JDBC SQLExceptions use the configured max.retries/retry.backoff.ms before record-level isolation/reporting when an errant-record reporter is available. Table provisioning failures follow a separate reporting path; database connection acquisition failures can stop a task without sending records to the DLQ. ksqlDB parser/UDF failures occur upstream and are not captured by the sink DLQ.

The repository has no automatic DLQ consumer, repair or replay flow. Diagnose using the context headers and worker logs, repair the cause, recover/replay through the supported source-offset or targeted republish procedure, then verify sink coverage before rerunning reconciliation. Message-inclusive error logging intentionally remains enabled for diagnostics. A DLQ record is not proof of a committed skip or a successful recovery.

The configured DLQ replication factor applies when Connect creates a missing topic; it does not change an existing topic's replication.

References: [Confluent JDBC sink DLQ behavior](https://docs.confluent.io/kafka-connectors/jdbc/current/sink-connector/overview.html#dead-letter-queue) and [Kafka 3.9 error reporting/tolerance implementation](https://github.com/apache/kafka/blob/3.9/connect/runtime/src/main/java/org/apache/kafka/connect/runtime/errors/RetryWithToleranceOperator.java).

## Deployment verification boundaries

- Before rerunning stream scripts, identify and terminate their existing persistent ksqlDB queries using the target version's supported lifecycle commands. `DROP ... IF EXISTS` does not terminate running queries. Do not drop the shared schema streams while any group depends on them.
- Supply complete, controlled reconciliation snapshots or rebuild the sinks externally. The baseline pipeline upserts emitted assets but does not delete a stored asset when a later record removes it or produces no rows; forwarding `OP_TYPE` is not an Oracle delete operation. QUICKCHECK does not quarantine records from the main parser.
- Verify stable Kafka keys/partition ordering for updates to the same `(RECID, ASSET_TYPE)`. JDBC upsert does not reject an older `COMMIT_TS`; multiple tasks do not establish global source-time ordering.
- Verify expected record/asset coverage and equivalent business cutoffs for R18/R25, not just zero connector lag. The report's exclusive lock protects its diff table, not synchronization of the two upstream sinks. Run the comparison procedure from a dedicated reporting session because its COMMIT also commits other work in that session.
- Validate actual UDF/Avro output types, registry schemas, timestamp/time-zone handling and Oracle field widths. Balances remain `NUMBER(38,4)` as in the baseline: more than four fractional digits are rounded, and more than 34 integer digits cannot fit. SQLite smoke does not verify this financial precision boundary.
- Message-inclusive worker error logging remains intentionally enabled for diagnosis. Restrict worker-log and DLQ access; with `errors.tolerance=none`, investigate failed tasks and verify coverage rather than assuming DLQ reporting allows continued processing.
- Verify execution plans and capacity on the target Oracle environment. `PARALLEL(8)` is a hint, not a guarantee of actual degree, and concurrently running reports can multiply resource demand.
