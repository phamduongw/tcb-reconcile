# Reconciliation deployment

1. Select the target DC or DR cluster first. If schema discovery/registration is required, run `F_STANDARD_SELECTION.sql` **once per cluster** for the R18/R25 schema-parser branch. Its inputs are `R18.F_STANDARD_SELECTION` and `R25.F_STANDARD_SELECTION`; its DROP statements recreate the parsed topics, so do not rerun it between groups on the same cluster. The business pipelines do not read these streams: they call `PARSE_T24_RECORD` with schema ID `6257` on DC or `6232` on DR, supplied by the owner for the schema containing CURRENCY. Verify the ID and schema content in the target registry; this script alone neither guarantees that ID nor proves it resolves to the expected schema.
2. Run `DDAY/R18_FBNK_EB_C005.sql` and `DDAY/R25_FBNK_EB_C005.sql` for DDAY. Run `DDAY/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `DDAY/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.
3. Run `RHS/R18_FBNK_EB_C005.sql` and `RHS/R25_FBNK_EB_C005.sql` for RHS. Run `RHS/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `RHS/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.

4. For DR, run the two stream scripts in `DDAYDR/` against DR ksqlDB, then `DDAYDR/report.sql` as `CONFLUENTDR` on the intended Oracle service before deploying its two connectors to DR Connect. Run only the comparison procedure again once both sinks have caught up and coverage is verified.

`DDAY/`, `RHS/` and `DDAYDR/` are sibling groups with independent Oracle sink tables, latest views, DIFF snapshot tables and comparison procedures. The RHS namespace cutover changes repository paths **and** stream/topic/connector names, Oracle object names, DIFF column names and historical missing-side labels. It is not a directory-only move. Deployed objects, rows, grants, external readers and connector offsets are not automatically renamed or migrated. Removing group files from the repository does not terminate deployed queries/connectors or delete external resources. Follow the RHS/date cutover below; the in-place rebuild instructions apply only when the target namespace already exists.

DC DDAY/RHS pipelines use schema ID `6257`; DR DDAYDR pipelines use `6232` for `EB_CONTRACT_BALANCES` including CURRENCY in `PARSE_T24_RECORD`. These are owner-supplied IDs; live registry/UDF validation remains a deployment check. Each derived stream projects `ROWKEY` to preserve the Kafka message key required by ksqlDB. `ROWKEY` is the message key, not a column in the Oracle sink tables; EXPLODED connectors append every record without a key. `EXPLODE_ASSET_BALANCES` uses business date `20261107` (07/11/2026) for both DDAY/DDAYDR sides and `20261031` (31/10/2026) for both RHS sides. This date difference is intentional; RHS also has the MAPPED cutoff documented below. Other balance transformations and comparison rules are shared.

All seven stream SQL scripts set `ksql.streams.num.stream.threads=8` immediately after `auto.offset.reset=earliest`. On a server that permits this override, it configures Kafka Streams runtimes created by subsequent statements; it does not resize already-running queries. The override persists in a CLI session, but REST SET assignments are scoped to one request, so submit SET and query creation together or use streamsProperties. Each runtime instance can use eight processing threads; useful parallelism remains limited by input partitions and available CPU. Classic transient push queries and stream pull queries built with Kafka Streams can inherit this setting; materialized-table pull queries and Oracle SELECT/COUNT do not acquire an eight-thread runtime from it. Confluent Cloud or server override restrictions can reject the setting; acceptance and actual thread counts require target-runtime verification. See [configuration restrictions](https://docs.confluent.io/platform/current/ksqldb/reference/server-configuration.html#ksql-properties-overrides-denylist) and the [upstream transient query builder](https://github.com/confluentinc/ksql/blob/master/ksqldb-engine/src/main/java/io/confluent/ksql/query/QueryBuilder.java).

Each report starts with a LAG section that points to the correct cluster's script: [lag.sh](lag.sh) for DC (`10.35.222.247:9092`), [DDAYDR/lag.sh](DDAYDR/lag.sh) for DR (`10.35.222.233:9092`). These scripts differ only in bootstrap address; DR keeps a local copy to avoid a DC default during monitoring. Each script takes one or more consumer group names as arguments, with no group names or count built in; the report gives the call for its two EXPLODED connector groups (`connect-<group>_<side>_FBNK_EB_C005_EXPLODED`, the Kafka Connect sink group name). Run it from the repository root on a host with `kafka-consumer-groups`. Each refresh describes all groups in one CLI call, because every call starts a JVM, then redraws the screen with the capture time and each group's total lag; it waits 2 seconds between refreshes, so the actual period also includes the CLI runtime. A partition without a committed offset counts its full log-end offset, and a group with no reported offsets is shown as such instead of as zero lag. If the CLI call fails, only its error output is shown. Stop it with Ctrl+C. Run the comparison only after both group lags stay at 0; zero connector lag alone does not prove ksqlDB has processed all source records. A CPU section follows that reads the `cpu_count` parameter from `V$PARAMETER`, to size the `PARALLEL` hints against the current instance; it needs SELECT access to that view (for example `SELECT_CATALOG_ROLE`) and has no hint. The report scripts DROP existing Oracle objects without an existence check; on first deployment, handle the expected missing-object errors or run only the CREATE section. Their final procedure invocation runs before the sinks have populated newly created tables. Each report compares only `OPEN_BAL`, `DR_MVT`, `CR_MVT` and `CLOSE_BAL` across matching and one-sided RECID/ASSET_TYPE pairs. Missing pairs use numeric NULL-to-zero normalization and the same currency-dependent threshold described below; metadata differences alone are not reported.

All three reports retain `/*+ PARALLEL(64) */` for the comparison SELECT and inspection queries; latest-view definitions do not force parallelism. REPORT contains the procedure invocation followed immediately by COUNT of the DIFF snapshot table. The separate COUNT section contains one `UNION ALL` query over the raw EXPLODED tables (R18, R25), returning one `SIDE`/`ROW_COUNT` row per side; the DIFF COUNT is not repeated, and views have no COUNT queries. INSPECT starts with one `UNION ALL` query over the latest EXPLODED views (R18, R25), labelled by a leading `SIDE` column and wrapped in an outer `SELECT /*+ PARALLEL(64) */ *` so its statement-level hint sits in the outermost query block and its `ORDER BY` applies to the combined result, followed by a single DIFF snapshot `SELECT *` query filtered with `WHERE RECID = ''` and ordered by `RECID, ASSET_TYPE`. Its displayed column order follows the actual Oracle table definition. Each comparison, COUNT or INSPECT SQL statement uses at most one `/*+ PARALLEL(64) */` hint: the comparison keeps it only on the outer SELECT, and the raw COUNT UNION ALL keeps it only on its first SELECT. Join-order, join-method, merge/predicate, distribution and index hints have been removed from all reports; the optimizer chooses those plan details. COUNT queries are unfiltered. Both INSPECT queries filter RECID (`WHERE v.RECID = ''` in both latest-view branches, `WHERE RECID = ''` in the final DIFF query): replace the empty strings with the intended RECID. Oracle treats an unchanged empty string as NULL, so it matches no rows. The view INSPECT union ends with `ORDER BY SIDE, CHANGED_TS`: all R18 rows appear first, ordered by CHANGED_TS ascending, followed by all R25 rows ordered by CHANGED_TS ascending. Rows sharing a timestamp within a side have no additional tie-breaker. Standalone `/` delimiters remain omitted for DBeaver. Execute each complete `CREATE ... PROCEDURE ... END;` or `BEGIN ... END;` block as one statement/selection, not as separate internal statements; SQL*Plus/SQLcl require a `/` after each complete PL/SQL block. Oracle decides whether to honor hints; verify actual plans in the target environment. Latest views use the compact `MAX + JOIN` form: the grouped subquery lists one column per line with aligned aliases, and the join condition stays on the single `) m ON ...;` line; DIFF table definitions and procedure INSERT/SELECT blocks retain one column per line. Independent statements are separated by one blank line. All SQL section headings use the stream convention: a title enclosed by two `-- ============================================================` lines, with one blank line before and after the heading block except at file start. KSQL preambles use SET followed by section headings; the shared F_STANDARD_SELECTION.sql retains its run-once note. Within each SELECT list, every single-line `expression AS alias` item aligns its AS after the longest single-line expression of that list plus one space, even when multi-line items sit between them; a multi-line expression closes with `) AS alias` or `END AS alias` and one space. Within each column or property list, column types and WITH property assignments align after the longest name plus one space. Streams and reports follow the same rules. RTRIM CASE expressions remain vertically aligned; logical blocks use four-space indentation with aligned expression continuations.

All SQL JOIN predicates keep the joined alias, ON and AND on the same line, including the closing `) m` of latest-view subqueries. Projection lists, section headings and other statement layouts retain the shared conventions above.

The connectors contain database credentials as requested: restrict access to these files and rotate the password if it is exposed. The Oracle wallet must exist at the configured path on every Kafka Connect worker.

All six EXPLODED connectors use `insert.mode=insert`, `pk.mode=none` with no `pk.fields`, `auto.create=false` and `auto.evolve=false`. Each uses `tasks.max=48`; verify 48 input partitions on each target cluster and the inherited derived-topic partition counts. This permits up to 48 sink tasks per connector, 192 across four DC connectors and 96 across two DR connectors, or 288 across DC and DR if both use the same database, before other connections/reporting overhead; verify Connect worker capacity and Oracle `sessions`/`processes` limits. Provision and verify the explicit report.sql table schemas before starting the connectors. Stop affected connectors before recreating sink tables; recreating tables does not reset committed offsets. Because the sinks append, any replay into a table that still holds earlier rows inserts every record again: rerunning the stream scripts drops and recreates the EXPLODED topics, and regenerating with a new business date emits new rows with the same `COMMIT_TS` and `POS`. Whenever the stream scripts are rerun, recreate the tables with `report.sql` and reset offsets or use fresh connector identities. Recover the complete required input through the supported offset-management interface or fresh connector identities when repopulating empty sinks. Earliest cannot restore expired/compacted records. Verify coverage on both sides before rerunning the comparison procedure, not the whole report script.

### End-to-end column order and symmetry

- RAW declarations place POS immediately after OP_TYPE and before OP_TS/CURRENT_TS. PARSED already uses the corresponding RECID/OP_TYPE/POS/COMMIT_TS/REPLICAT_TS order, with DATA last.
- MAPPED preserves that prefix and adds MAPPED_TS, then S fields in CURRENCY/APPLICATION/CUSTOMER/DATE_LAST_UPDATE/HVT_FLAG order, then BALANCE, then A fields in CURR_ASSET_TYPE/OPEN_BALANCE/DEBIT_MVMT/CREDIT_MVMT/TYPE_SYSDATE order.
- EXPLODED adds ASSET_TYPE immediately after RECID, then the operation/version/timestamp prefix, the same S metadata fields, OPEN_BAL/DR_MVT/CR_MVT/CLOSE_BAL and the same A fields. Its 22 value columns match Oracle EXPLODED DDL order after excluding CHANGED_TS, which Oracle generates. ROWKEY is a Kafka key, not an Oracle column.
- R18/R25 scripts are identical after side-name normalization. Across RHS/DDAY/DDAYDR, the only stream-SQL differences after namespace normalization are business date, parser schema ID and the explicitly retained RHS-only cutoff. Routing, Oracle owner/account and registry/broker differences remain required environment configuration, not comparison-rule differences.
- DATA is a map, not an ordered set of relational columns; existing parser-schema aliases/types are preserved and CURRENCY/c1 is added; parser IDs are DC `6257` and DR `6232`. This repository does not change the field order in existing upstream OGG/Avro messages. Derived-stream projection order changes must be deployed through the supported query lifecycle and checked against registered Avro schemas and downstream consumers; no schema registration or live query replacement is performed by editing these files. Do not run destructive DROP/rebuild sections merely to reorder columns.

## RHS MAPPED cutoff

Only RHS R18/R25 MAPPED streams add the following condition alongside the existing asset-type check:

```sql
WHERE DATA['CURR_ASSET_TYPE'] IS NOT NULL
  AND COMMIT_TS < PARSE_TIMESTAMP('2026-11-01 10:10:00.000000', 'yyyy-MM-dd HH:mm:ss.SSSSSS')
```

The fixed cutoff is November 1, 2026 at 10:10 AM, the date requested as "today" in the +07 operator session. Exactly 10:10:00 and later are excluded. The literal uses the same PARSE_TIMESTAMP format/convention as COMMIT_TS in PARSED; no additional time-zone conversion is introduced. This is a constant cutoff, not a rolling daily rule. DDAY and DDAYDR have no cutoff. HVT_FLAG is not a filter.

Filtering happens at RHS MAPPED, not RAW, PARSED or Oracle views. Records rejected there emit no new MAPPED/EXPLODED asset rows. Oracle latest views and comparison procedures have no time filter; the comparison and missing-normalization rules below apply. Editing the files does not alter a running persistent query or remove post-cutoff records already in MAPPED/EXPLODED topics or Oracle tables. Before relying on the cutoff for a full historical report, coordinate query recreation and a controlled replay/sink-content reconciliation; existing later versions in Oracle can still win the latest view. Do not blindly run DROP/rebuild scripts or purge data.

## Latest EXP reconciliation baseline

The latest-view definitions and their consumers are owned by each group's `report.sql`, for example [RHS/report.sql](RHS/report.sql). "Latest" means every stored EXPLODED row at the greatest `COMMIT_TS` for its `RECID` and, among rows at that timestamp, the greatest `POS`; it is not one row per RECID and not the greatest version separately for each asset. `POS` is the GoldenGate trail position. It is carried unchanged as a string from the source stream through PARSED, MAPPED and EXPLODED and stored in Oracle as `NUMBER(20)`, so the latest view compares it numerically. The JDBC sink writes the string and Oracle converts it on insert; a non-numeric `POS` fails the sink task. `POS` only breaks ties between source records that share `COMMIT_TS`, for example operations in the same transaction or within the same millisecond. Assets emitted by that latest record must all remain available to reconciliation. R18 and R25 determine their own latest versions; equality between the two sides' timestamps or positions is not a comparison rule. The sink tables have no primary key. Their nonunique `(RECID, COMMIT_TS, POS)` index serves the view's per-RECID maximum and RECID inspection. These indexes remain available for latest-version/RECID lookups and COUNT access paths; no index access method is forced by a hint. RECID is NOT NULL, so every sink row has an entry in its index.

The reconciliation path is EXPLODED sink tables -> `V_<group>_<side>_FBNK_EB_C005_EXPLODED` -> comparison procedure with inline DIFF SQL -> DIFF snapshot table. The procedure owns the full outer join, missing-only numeric normalization, NULL-safe balance comparisons with currency-dependent thresholds, missing classification and deltas; no DIFF view is created or queried. Keys from either latest dataset are considered, but missing pairs whose normalized differences do not exceed their currency threshold are omitted. Run the procedure, then read COUNT and the filtered DIFF INSPECT query from the stored DIFF table. Both read the saved result rather than recomputing against current upstream data. Raw COUNT reports all stored sink rows, including older versions and assets; latest INSPECT shows the live report inputs. Latest views are live, while the DIFF table changes only when its comparison procedure runs. Separate COUNT and INSPECT reads are not pinned to a run: another successful refresh between them can replace the saved snapshot. Avoid concurrent refreshes while reading if both statements must describe the same saved result.

### Matched and missing comparisons with currency-dependent thresholds

The latest views are combined with FULL OUTER JOIN on `(RECID, ASSET_TYPE)`. An inline query defines the comparison values for each pair:

- **Both rows exist:** preserve all four balances, including NULL. NULL/NULL is equal; one NULL versus any number (including 0 or +/-1) is a mismatch with a NULL delta, exactly as before.
- **One row is missing:** convert every NULL in the four balances on either side of this pair to 0. This includes the absent side and nullable balances on the existing side. Use these normalized values both in the eight displayed balance columns and in the signed `R25 - R18` deltas. Existing non-NULL balances are unchanged. Metadata is never normalized; the absent side's metadata stays NULL.

CURRENCY is guaranteed non-NULL on existing input rows; the absent side of a missing pair naturally has NULL metadata. Since equality of the two currencies is not guaranteed, choose the conservative threshold: 1 only when every existing side is exactly VND, otherwise 0. Thus both matched sides must be VND for threshold 1; a missing pair uses its existing side's currency. Different currencies use threshold 0 in either direction. No FX conversion or standalone currency-mismatch classification is added. The same predicate is used for OPEN_BAL, DR_MVT, CR_MVT and CLOSE_BAL in WHERE and DIFF_COLUMNS. Here `c.R18_OPEN_BAL` and `c.R25_OPEN_BAL` are the conditional comparison values above:

```sql
DECODE(
    c.R18_OPEN_BAL, c.R25_OPEN_BAL, 0,
    CASE WHEN ABS(c.R25_OPEN_BAL - c.R18_OPEN_BAL) <= c.DIFF_THRESHOLD
         THEN 0 ELSE 1 END
) = 1
```

A row is retained only if at least one field has a reportable mismatch. For VND, report numeric differences only when ABS(delta) > 1: 0.01, 0.5 and exactly +/-1 are excluded, while +/-1.0001 are reported. For non-VND, report whenever ABS(delta) > 0, including +/-1 and fractional differences. This replaces the former exact-unit exemption. Matched numeric NULL mismatches retain their separate rule above. For a missing VND pair with R18 balances `(200, NULL, 1, -1)`, display R18 as `(200, 0, 1, -1)`, R25 as `(0, 0, 0, 0)`, deltas as `(-200, 0, -1, 1)` and DIFF_COLUMNS as OPEN_BAL. For the same balances in USD, DIFF_COLUMNS is OPEN_BAL, CR_MVT, CLOSE_BAL.

DIFF_COLUMNS lists only fields that exceed the applicable threshold, plus matched NULL-versus-number mismatches. All signed deltas in retained rows are preserved. For example, `(1, -1, 0, 200)` labels only CLOSE_BAL for VND, but OPEN_BAL, DR_MVT, CLOSE_BAL for non-VND.

DIFF_TYPE uses the same side-only labels in every group; the group is identified by the DIFF table that stores the row:

| Type | Meaning |
| --- | --- |
| `VALUE_MISMATCH` | Both latest-view rows exist; at least one balance is reported as different. |
| `MISSING_RECID_IN_R18` | No row for this RECID exists in the R18 latest view. |
| `MISSING_RECID_IN_R25` | No row for this RECID exists in the R25 latest view. |
| `MISSING_ASSET_TYPE_IN_R18` | R18 has the RECID but not this ASSET_TYPE. |
| `MISSING_ASSET_TYPE_IN_R25` | R25 has the RECID but not this ASSET_TYPE. |

RECID presence comes from two internal `COUNT(side.RECID) OVER (PARTITION BY COALESCE(r18.RECID, r25.RECID))` expressions on the same full-join result. These counts are computed before the outer balance filter. A different asset with equal or below-threshold balances therefore still establishes that the RECID exists. A zero count identifies a missing RECID; otherwise the row's missing-side flag identifies a missing ASSET_TYPE. Missing status does not bypass the balance filter. These are internal presence checks, not extra output columns or coverage counters.

The comparison has one FULL OUTER JOIN, references each latest view once and has no correlated RECID lookup or additional existence join. The inner query handles presence counts, threshold selection and missing-only normalization; the outer query handles filtering and output. The two counts share the same partition definition, but may require a WINDOW SORT over the joined rows. This removes repeated view references, not all processing cost. Only PARALLEL(64) hints remain: one on the outer SELECT of each comparison statement, none on its inner SELECT. Each COUNT/INSPECT statement likewise has one hint; the raw COUNT UNION ALL keeps it only on the first branch. Oracle documents this no-table form as a [statement-level PARALLEL hint](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Comments.html#GUID-D25225CE-2DCE-4D9F-8E82-401839690A6E), so repeating the same degree in nested blocks is unnecessary here. It does not add the degrees together. The requested degree 64 is retained, not certified optimal; actual parallelism depends on restrictions, resources and the resulting plan. No parallel-DML mode, APPEND or other execution option is enabled by this change. Index DDL is unchanged. Verify the actual Oracle plan, memory/TEMP use and elapsed time: this structural simplification is not proof of the fastest plan or guaranteed materialization.

The 26-column DIFF order is RECID, ASSET_TYPE, DIFF_COLUMNS, DIFF_TYPE, then the ten paired S fields (CURRENCY, APPLICATION, CUSTOMER, DATE_LAST_UPDATE and HVT_FLAG), then the eight per-side balances, and finally DIFF_OPEN_BAL, DIFF_DR_MVT, DIFF_CR_MVT and DIFF_CLOSE_BAL. Each pair keeps R18 before R25. DDL, INSERT and SELECT use this order. INSPECT remains `SELECT *`, so its display follows the actual Oracle table order. Adding a column or replacing a procedure does not reorder an existing table; exact display order requires a separately controlled schema migration. ## JDBC sink DLQ policy

Each EXPLODED connector uses the side-specific `<group>_<side>.SINK_ERROR` destination. Context headers identify the original topic/partition/offset, connector/task, failure stage and exception details. The DLQ retains the failed original key/value bytes, not an Oracle error table or a new business-record schema. Restrict topic/table/DLQ access because these records contain customer and balance data.

The baseline keeps `errors.tolerance=none`: failures are not silently skipped so reconciliation can continue with missing records. In upstream Kafka Connect error handling, a record may be reported to the DLQ before the tolerance check fails the task; a failed task therefore does not prove the DLQ is empty, and a configured DLQ does not guarantee delivery or continued processing. Validate the installed Kafka Connect/JDBC versions and actual task/DLQ state before relying on this behavior.

JDBC SQLExceptions use the configured max.retries/retry.backoff.ms before record-level isolation/reporting when an errant-record reporter is available. Table provisioning failures follow a separate reporting path; database connection acquisition failures can stop a task without sending records to the DLQ. ksqlDB parser/UDF failures occur upstream and are not captured by the sink DLQ.

The repository has no automatic DLQ consumer, repair or replay flow. Diagnose using the context headers and worker logs, repair the cause, recover/replay through the supported source-offset or targeted republish procedure, then verify sink coverage before rerunning reconciliation. Message-inclusive error logging intentionally remains enabled for diagnostics. A DLQ record is not proof of a committed skip or a successful recovery.

The configured DLQ replication factor applies when Connect creates a missing topic; it does not change an existing topic's replication.

References: [Confluent JDBC sink DLQ behavior](https://docs.confluent.io/kafka-connectors/jdbc/current/sink-connector/overview.html#dead-letter-queue) and [Kafka 3.9 error reporting/tolerance implementation](https://github.com/apache/kafka/blob/3.9/connect/runtime/src/main/java/org/apache/kafka/connect/runtime/errors/RetryWithToleranceOperator.java).
