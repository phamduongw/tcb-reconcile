1. If schema discovery/registration is required, run `F_STANDARD_SELECTION.sql` **once** for the R18/R25 schema-parser branch. Its inputs are `R18.F_STANDARD_SELECTION` and `R25.F_STANDARD_SELECTION`; its DROP statements recreate the parsed topics, so do not rerun it between groups. The business pipelines do not read these streams: they call `PARSE_T24_RECORD` with fixed schema ID `6226`. Verify that ID in the target registry; this script alone does not prove it resolves to the expected schema.
2. Run `DDAY/R18_FBNK_EB_C005.sql` and `DDAY/R25_FBNK_EB_C005.sql` for DDAY. Run `DDAY/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `DDAY/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.
3. Run `RHS/R18_FBNK_EB_C005.sql` and `RHS/R25_FBNK_EB_C005.sql` for RHS. Run `RHS/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `RHS/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.

`DDAY/` and `RHS/` are sibling groups with independent Oracle sink tables, latest views, DIFF snapshot tables and comparison procedures. The RHS namespace cutover changes repository paths **and** stream/topic/connector names, Oracle object names, DIFF column names and missing-side labels. It is not a directory-only move. Deployed objects, rows, grants, external readers and connector offsets are not automatically renamed or migrated. Removing group files from the repository does not terminate deployed queries/connectors or delete external resources. Follow the RHS/date cutover below; the in-place rebuild instructions apply only when the target namespace already exists.

All DDAY/RHS ksqlDB pipelines use schema ID `6226` for `EB_CONTRACT_BALANCES` in `PARSE_T24_RECORD`. Each derived stream projects `ROWKEY` to preserve the Kafka message key required by ksqlDB. `ROWKEY` is the message key, not a column in the Oracle sink tables; EXPLODED connectors append every record without a key. `EXPLODE_ASSET_BALANCES` uses business date `20261107` (07/11/2026) for both DDAY sides and `20261031` (31/10/2026) for both RHS sides. This date difference is intentional; all other business transformation and comparison rules are shared.

All five stream SQL scripts set `ksql.streams.num.stream.threads=8` immediately after `auto.offset.reset=earliest`. On a server that permits this override, it configures Kafka Streams runtimes created by subsequent statements; it does not resize already-running queries. The override persists in a CLI session, but REST SET assignments are scoped to one request, so submit SET and query creation together or use streamsProperties. Each runtime instance can use eight processing threads; useful parallelism remains limited by input partitions and available CPU. Classic transient push queries and stream pull queries built with Kafka Streams can inherit this setting; materialized-table pull queries and Oracle SELECT/COUNT do not acquire an eight-thread runtime from it. Confluent Cloud or server override restrictions can reject the setting; acceptance and actual thread counts require target-runtime verification. See [configuration restrictions](https://docs.confluent.io/platform/current/ksqldb/reference/server-configuration.html#ksql-properties-overrides-denylist) and the [upstream transient query builder](https://github.com/confluentinc/ksql/blob/master/ksqldb-engine/src/main/java/io/confluent/ksql/query/QueryBuilder.java).

The report scripts DROP existing Oracle objects without an existence check; on first deployment, handle the expected missing-object errors or run only the CREATE section. Their final procedure invocation runs before the sinks have populated newly created tables. Each report compares only `OPEN_BAL`, `DR_MVT`, `CR_MVT`, `CLOSE_BAL` and row presence, not metadata fields.

Both reports retain `/*+ PARALLEL(64) */` for the comparison SELECT and inspection queries; latest-view definitions do not force parallelism. REPORT contains the procedure invocation followed immediately by COUNT of the DIFF snapshot table. The separate COUNT section contains one `UNION ALL` query over the raw EXPLODED tables (R18, R25), returning one `SIDE`/`ROW_COUNT` row per side; the DIFF COUNT is not repeated, and views have no COUNT queries. INSPECT contains one `UNION ALL` query over the latest EXPLODED views (R18, R25), labelled by a leading `SIDE` column and wrapped in an outer `SELECT *` so its `ORDER BY` applies to the combined result, then a separate query on the DIFF snapshot table. Each raw EXPLODED branch of the COUNT union retains `INDEX_FFS(t)`; DIFF COUNT and INSPECT queries do not force an index. COUNT queries are unfiltered. Every INSPECT filter compares RECID with an empty string (`WHERE v.RECID = ''` in both union branches, `WHERE RECID = ''` on the DIFF table): replace each empty string with the intended RECID; Oracle treats the unchanged empty string as NULL, so it matches no rows. The view INSPECT union ends with `ORDER BY CHANGED_TS`; the DIFF INSPECT query has no ORDER BY. Standalone `/` delimiters remain omitted for DBeaver. Execute each complete `CREATE ... PROCEDURE ... END;` or `BEGIN ... END;` block as one statement/selection, not as separate internal statements; SQL*Plus/SQLcl require a `/` after each complete PL/SQL block. Oracle decides whether to honor hints; verify actual plans in the target environment. Latest views use the compact `MAX + JOIN` form: the grouped subquery lists one column per line with aligned aliases, and the join condition stays on the single `) m ON ...;` line; DIFF table definitions and procedure INSERT/SELECT blocks retain one column per line. Independent statements are separated by one blank line. All SQL section headings use the stream convention: a title enclosed by two `-- ============================================================` lines, with one blank line before and after the heading block except at file start. KSQL preambles use SET followed by section headings; the shared F_STANDARD_SELECTION.sql retains its run-once note. Within each consecutive group, AS aliases, column types and WITH property assignments align after the longest expression/name plus one space, following the source streams. RTRIM CASE expressions remain vertically aligned; logical blocks use four-space indentation with aligned expression continuations.

All SQL JOIN predicates keep the joined alias, ON and AND on the same line, including the closing `) m` of latest-view subqueries. Projection lists, section headings and other statement layouts retain the shared conventions above.

The connectors contain database credentials as requested: restrict access to these files and rotate the password if it is exposed. The Oracle wallet must exist at the configured path on every Kafka Connect worker.

All four EXPLODED connectors use `insert.mode=insert`, `pk.mode=none` with no `pk.fields`, `auto.create=false` and `auto.evolve=false`. Provision and verify the explicit report.sql table schemas before starting the connectors. Stop affected connectors before recreating sink tables; recreating tables does not reset committed offsets. Because the sinks append, any replay into a table that still holds earlier rows inserts every record again: rerunning the stream scripts drops and recreates the EXPLODED topics, and regenerating with a new business date emits new rows with the same `COMMIT_TS` and `POS`. Whenever the stream scripts are rerun, recreate the tables with `report.sql` and reset offsets or use fresh connector identities. Recover the complete required input through the supported offset-management interface or fresh connector identities when repopulating empty sinks. Earliest cannot restore expired/compacted records. Verify coverage on both sides before rerunning the comparison procedure, not the whole report script.

## Latest EXP reconciliation baseline

The latest-view definitions and their consumers are owned by each group's `report.sql`, for example [RHS/report.sql](RHS/report.sql). "Latest" means every stored EXPLODED row at the greatest `COMMIT_TS` for its `RECID` and, among rows at that timestamp, the greatest `POS`; it is not one row per RECID and not the greatest version separately for each asset. `POS` is the GoldenGate trail position. It is carried unchanged as a string from the source stream through PARSED, MAPPED and EXPLODED and stored in Oracle as `NUMBER(20)`, so the latest view compares it numerically. The JDBC sink writes the string and Oracle converts it on insert; a non-numeric `POS` fails the sink task. `POS` only breaks ties between source records that share `COMMIT_TS`, for example operations in the same transaction or within the same millisecond. Assets emitted by that latest record must all remain available to reconciliation. R18 and R25 determine their own latest versions; equality between the two sides' timestamps or positions is not a comparison rule. The sink tables have no primary key. Their nonunique `(RECID, COMMIT_TS, POS)` index serves the view's per-RECID maximum, the procedure's per-RECID missing-record lookups and RECID inspection; because `RECID` is NOT NULL, it also holds every row for the raw `INDEX_FFS` COUNT.

The reconciliation path is EXPLODED sink tables -> `V_<group>_<side>_FBNK_EB_C005_EXPLODED` -> comparison procedure with inline DIFF SQL -> DIFF snapshot table. The procedure owns the full outer join, null-safe balance comparisons, missing-record/asset classification and deltas; no DIFF view is created or queried. Missing-record classification uses the same latest dataset as the full outer join, not raw EXPLODED history. Run the procedure, then read COUNT and filtered INSPECT from the stored DIFF table. Both read the saved result rather than recomputing against current upstream data. Raw COUNT reports all stored sink rows, including older versions and assets; latest INSPECT shows the live report inputs. Latest views are live, while the DIFF table changes only when its comparison procedure runs. Separate COUNT and INSPECT reads are not pinned to a run: another successful refresh between them can replace the saved snapshot. Avoid concurrent refreshes while reading if both statements must describe the same saved result.

For an existing populated deployment, the current sink change cannot be applied in place: the EXPLODED tables gain `POS` and `CHANGED_TS`, lose the `(RECID, ASSET_TYPE)` primary key and switch from upsert to append, and the latest views and `(RECID, COMMIT_TS, POS)` indexes change with them. Stop the group's connectors and terminate its persistent queries, rerun its two stream scripts and `report.sql` to recreate the streams, tables, index, views, DIFF table and procedure, then replay into the empty tables with supported offset reset or fresh connector identities. Re-grant reader permissions after recreation, rerun the procedure after both sides have reached the intended cutoff, and schedule the rebuild without concurrent reporting. Previous DIFF views (`V_<group>_R18_R25_FBNK_EB_C005_DIFF`) are not used; drop them once external readers use the snapshot table.

Operating assumptions and deployment notes (accepted by the owner; not symmetry defects):

- `COMMIT_TS` and `POS` are guaranteed non-null by the source contract. Keep the MAX-equality semantics; do not add a fallback timestamp or position or a redundant NULL filter. Rows stored before `POS` was added have NULL `POS` and are never selected, so rebuild the sinks from retained input when deploying this change.
- Supply complete emitted asset snapshots per RECID. The sink appends every emitted row and keeps all versions; the latest view selects the newest version per RECID regardless of arrival order. A newer emitted batch hides older stored assets, but a version emitting no EXPLODED rows or a delete cannot advance the view's maximum. Delivery is at-least-once: a connector restart or rebalance can insert the same record twice, and the latest view then returns both copies, which repeats the affected DIFF rows when that key differs or is missing on one side. The tables grow with every change, so plan retention for old versions.
- Complete both R18/R25 asset batches before comparing. One row arriving at a newer timestamp immediately advances the live view and temporarily hides the remaining older rows. Zero lag alone does not prove asset coverage, ordering, or equivalent business cutoffs; the report lock does not freeze either sink.
- Confirm `COMMIT_TS` identifies versions at the pipeline's effective timestamp precision, including Oracle `TIMESTAMP(3)`. Distinct versions sharing the stored timestamp are separated by `POS`; `POS` must increase with source order within each side, which holds while the GoldenGate trail sequence is not reset.
- Validate Oracle object compilation, direct object privileges, dependencies, index definitions/statistics, actual plans and report capacity on the target environment. Reporting users need EXECUTE permission on the comparison procedure and SELECT permission on the DIFF snapshot table; latest-view inspection also needs SELECT on those views. Existing table/view grants are not interchangeable; verify reader permissions when migrating from the removed DIFF view.
- Validate registry schema `6226`, external parser/balance UDFs, Avro types, timestamp/time-zone handling and the intended business date (`20261107` for DDAY; `20261031` for RHS). Local SQL adaptation cannot establish these runtime contracts.
- Review the existing embedded credentials, disabled database TLS DN matching, HTTP Schema Registry and message-inclusive error logging against the target environment's security policy. These settings are not validated or hardened by the latest-view cutover.

Earlier verification of the procedure-based workflow (historical evidence, not the current review run): actual report DDL, latest-view queries, procedure DELETE/INSERT SQL and diagnostic SELECTs were executed in isolated in-memory SQLite databases for DDAY and RHS. The inline procedure produced the same 22 saved columns as the prior view-backed procedure for controlled fixtures covering tied latest assets, stale-asset exclusion, independent timestamps, individual/multiple balance mismatches, NULL equality versus NULL/zero, metadata-only differences, missing records/assets on both sides and signed deltas. COUNT and DIFF INSPECT remained on the stored result after upstream changes until refresh; repeated and empty refreshes and teardown also passed. Group-normalized reports matched, and the other ten repository artifacts were unchanged. SQLite adaptations covered Oracle DECODE, NULL concatenation, CREATE VIEW and index syntax, not Oracle compilation, PL/SQL execution/locks/rollback, financial precision, live ksqlDB/UDF/Avro or Kafka Connect. No Oracle SQL client or accessible local container runtime was available, so target-runtime and security release gates remain open.

Accepted operating conditions (owner-confirmed; retained for context, not outstanding defects or blockers for this symmetry review):

## JDBC sink DLQ policy

Each EXPLODED connector uses the side-specific `<group>_<side>.SINK_ERROR` destination. Context headers identify the original topic/partition/offset, connector/task, failure stage and exception details. The DLQ retains the failed original key/value bytes, not an Oracle error table or a new business-record schema. Restrict topic/table/DLQ access because these records contain customer and balance data.

The baseline keeps `errors.tolerance=none`: failures are not silently skipped so reconciliation can continue with missing records. In upstream Kafka Connect error handling, a record may be reported to the DLQ before the tolerance check fails the task; a failed task therefore does not prove the DLQ is empty, and a configured DLQ does not guarantee delivery or continued processing. Validate the installed Kafka Connect/JDBC versions and actual task/DLQ state before relying on this behavior.

JDBC SQLExceptions use the configured max.retries/retry.backoff.ms before record-level isolation/reporting when an errant-record reporter is available. Table provisioning failures follow a separate reporting path; database connection acquisition failures can stop a task without sending records to the DLQ. ksqlDB parser/UDF failures occur upstream and are not captured by the sink DLQ.

The repository has no automatic DLQ consumer, repair or replay flow. Diagnose using the context headers and worker logs, repair the cause, recover/replay through the supported source-offset or targeted republish procedure, then verify sink coverage before rerunning reconciliation. Message-inclusive error logging intentionally remains enabled for diagnostics. A DLQ record is not proof of a committed skip or a successful recovery.

The configured DLQ replication factor applies when Connect creates a missing topic; it does not change an existing topic's replication.

References: [Confluent JDBC sink DLQ behavior](https://docs.confluent.io/kafka-connectors/jdbc/current/sink-connector/overview.html#dead-letter-queue) and [Kafka 3.9 error reporting/tolerance implementation](https://github.com/apache/kafka/blob/3.9/connect/runtime/src/main/java/org/apache/kafka/connect/runtime/errors/RetryWithToleranceOperator.java).

## Deployment verification boundaries

- Before rerunning stream scripts, identify and terminate their existing persistent ksqlDB queries using the target version's supported lifecycle commands. `DROP ... IF EXISTS` does not terminate running queries. Do not drop the shared schema streams while any group depends on them.
- Supply complete, controlled reconciliation snapshots or rebuild the sinks externally. The pipeline appends emitted assets and does not delete a stored asset when a later record removes it or produces no rows; forwarding `OP_TYPE` is not an Oracle delete operation.
- Append mode does not rely on Kafka partition ordering: every version is kept and the latest view orders by `COMMIT_TS` and then `POS`. Multiple tasks still insert in no global order, so neither arrival order nor `CHANGED_TS` identifies the latest version.
- Verify expected record/asset coverage and equivalent business cutoffs for R18/R25, not just zero connector lag. The report's exclusive lock protects its diff table, not synchronization of the two upstream sinks. Run the comparison procedure from a dedicated reporting session because its COMMIT also commits other work in that session.
- Validate actual UDF/Avro output types, registry schemas, timestamp/time-zone handling and Oracle field widths. Balances remain `NUMBER(38,4)` as in the baseline: more than four fractional digits are rounded, and more than 34 integer digits cannot fit. SQLite smoke does not verify this financial precision boundary.
- Message-inclusive worker error logging remains intentionally enabled for diagnosis. Restrict worker-log and DLQ access; with `errors.tolerance=none`, investigate failed tasks and verify coverage rather than assuming DLQ reporting allows continued processing.
- Verify execution plans and capacity on the target Oracle environment. `PARALLEL(64)` is a hint, not a guarantee of actual degree, and concurrently running reports can multiply resource demand.
