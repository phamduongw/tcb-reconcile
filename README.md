# Reconciliation deployment

1. Run `F_STANDARD_SELECTION.sql` **once** to create the shared R18/R25 source and parsed streams for both DDAY and RHS1. Its DROP statements recreate the parsed topics; do not rerun it between groups. The shared input topics are `R18.F_STANDARD_SELECTION` and `R25.F_STANDARD_SELECTION`.
2. Run `DDAY/R18_FBNK_EB_C005.sql` and `DDAY/R25_FBNK_EB_C005.sql` for DDAY. Run `DDAY/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `DDAY/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.
3. Run `RHS1/R18_FBNK_EB_C005.sql` and `RHS1/R25_FBNK_EB_C005.sql` for RHS1. Run `RHS1/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `RHS1/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.

`DDAY/` and `RHS1/` are sibling groups with independent Oracle sink tables, latest views, DIFF snapshot tables and comparison procedures. Moving RHS1 changes repository paths only; stream/topic/connector names, Oracle object names and committed offsets remain unchanged. Do not recreate deployed objects just because files moved. Removing group files from the repository does not terminate deployed queries/connectors or delete external resources.

All DDAY/RHS1 ksqlDB pipelines use schema ID `6226` for `EB_CONTRACT_BALANCES` in `PARSE_T24_RECORD`. Each derived stream projects `ROWKEY` to preserve the Kafka message key required by ksqlDB. `ROWKEY` is the message key, not a column in the Oracle sink tables; EXPLODED connectors use `RECID, ASSET_TYPE` from the record value as their upsert primary key. Confirm the hard-coded `20261003` used by `EXPLODE_ASSET_BALANCES` matches the intended reconciliation date.

All five stream SQL scripts set `ksql.streams.num.stream.threads=8` immediately after `auto.offset.reset=earliest`. On a server that permits this override, it configures Kafka Streams runtimes created by subsequent statements; it does not resize already-running queries. The override persists in a CLI session, but REST SET assignments are scoped to one request, so submit SET and query creation together or use streamsProperties. Each runtime instance can use eight processing threads; useful parallelism remains limited by input partitions and available CPU. Classic transient push queries and stream pull queries built with Kafka Streams can inherit this setting; materialized-table pull queries and Oracle SELECT/COUNT do not acquire an eight-thread runtime from it. Confluent Cloud or server override restrictions can reject the setting; acceptance and actual thread counts require target-runtime verification. See [configuration restrictions](https://docs.confluent.io/platform/current/ksqldb/reference/server-configuration.html#ksql-properties-overrides-denylist) and the [upstream transient query builder](https://github.com/confluentinc/ksql/blob/master/ksqldb-engine/src/main/java/io/confluent/ksql/query/QueryBuilder.java).

The report scripts DROP existing Oracle objects without an existence check; on first deployment, handle the expected missing-object errors or run only the CREATE section. Their final procedure invocation runs before the sinks have populated newly created tables. Each report compares only `OPEN_BAL`, `DR_MVT`, `CR_MVT`, `CLOSE_BAL` and row presence, not metadata fields.

Both reports retain `/*+ PARALLEL(8) */` for the comparison SELECT and inspection queries; latest-view definitions do not force parallelism. REPORT contains the procedure invocation followed immediately by COUNT of the DIFF snapshot table. The separate COUNT section contains only raw EXPLODED tables (R18, R25); the DIFF COUNT is not repeated, and views have no COUNT queries. INSPECT contains latest EXPLODED views (R18, R25), then the DIFF snapshot table. Raw EXPLODED COUNT queries retain `INDEX_FFS(t)`; DIFF COUNT and INSPECT queries do not force an index. COUNT queries are unfiltered and occupy two lines. INSPECT queries occupy three lines and end with `WHERE RECID = '';`: replace the empty string with the intended RECID; Oracle treats the unchanged empty string as NULL, so it matches no rows. No inspection query includes ORDER BY. Standalone `/` delimiters remain omitted for DBeaver. Execute each complete `CREATE ... PROCEDURE ... END;` or `BEGIN ... END;` block as one statement/selection, not as separate internal statements; SQL*Plus/SQLcl require a `/` after each complete PL/SQL block. Oracle decides whether to honor hints; verify actual plans in the target environment. Latest views use the compact `MAX + JOIN` form; DIFF table definitions and procedure INSERT/SELECT blocks retain one column per line. Independent statements are separated by one blank line. All SQL section headings use the stream convention: a title enclosed by two `-- ============================================================` lines, with one blank line before and after the heading block except at file start. KSQL preambles use SET followed by section headings; the shared F_STANDARD_SELECTION.sql retains its run-once note. Within each consecutive group, AS aliases, column types and WITH property assignments align after the longest expression/name plus one space, following the source streams. RTRIM CASE expressions remain vertically aligned; logical blocks use four-space indentation with aligned expression continuations.

All SQL JOIN predicates keep the joined alias, ON and AND on the same line, including the closing `) m` of latest-view subqueries. Projection lists, section headings and other statement layouts retain the shared conventions above.

The connectors contain database credentials as requested: restrict access to these files and rotate the password if it is exposed. The Oracle wallet must exist at the configured path on every Kafka Connect worker.

All four EXPLODED connectors use `insert.mode=upsert`, `pk.mode=record_value`, `pk.fields=RECID, ASSET_TYPE`, `auto.create=false` and `auto.evolve=false`. Provision and verify the explicit report.sql table schemas before starting the connectors. Stop affected connectors before recreating sink tables; recreating tables does not reset committed offsets. Recover the complete required input through the supported offset-management interface or fresh connector identities when repopulating empty sinks. Earliest cannot restore expired/compacted records. Verify coverage on both sides before rerunning the comparison procedure, not the whole report script.

## Latest EXP reconciliation baseline

The latest-view definitions and their consumers are owned by each group's `report.sql`, for example [RHS1/report.sql](RHS1/report.sql). "Latest" means every stored EXPLODED row at the greatest `COMMIT_TS` for its `RECID`, not one row per RECID and not the greatest timestamp separately for each asset. Assets tied at that timestamp must all remain available to reconciliation. R18 and R25 determine their own latest timestamps; equality between the two sides' timestamps is not a comparison rule.

The reconciliation path is EXPLODED sink tables -> `V_<group>_<side>_FBNK_EB_C005_EXPLODED` -> comparison procedure with inline DIFF SQL -> DIFF snapshot table. The procedure owns the full outer join, null-safe balance comparisons, missing-record/asset classification and deltas; no DIFF view is created or queried. Missing-record classification uses the same latest dataset as the full outer join, not raw EXPLODED history. Run the procedure, then read COUNT and filtered INSPECT from the stored DIFF table. Both read the saved result rather than recomputing against current upstream data. Raw COUNT reports all stored sink rows, including older assets; latest INSPECT shows the live report inputs. Latest views are live, while the DIFF table changes only when its comparison procedure runs. Separate COUNT and INSPECT reads are not pinned to a run: another successful refresh between them can replace the saved snapshot. Avoid concurrent refreshes while reading if both statements must describe the same saved result.

For an existing populated deployment, verify the DIFF table's 22 columns against the explicit CREATE TABLE definition and apply `CREATE OR REPLACE PROCEDURE` from that group's report. Keep the existing sink and DIFF tables, their rows and grants; do not run DROP TABLE or CREATE TABLE during this procedure cutover. Latest views and nonunique `(RECID, COMMIT_TS)` indexes are unchanged; provision them only if missing and verify existing definitions. Validate procedure compilation, dependencies and grants, migrate any external DIFF-view readers to the snapshot table, then remove the previous DIFF views once with `DROP VIEW CONFLUENT.V_DDAY_R18_R25_FBNK_EB_C005_DIFF;` and `DROP VIEW CONFLUENT.V_RHS1_R18_R25_FBNK_EB_C005_DIFF;`. Rerun the procedure after both sides have reached the intended cutoff. Oracle DDL commits independently; archive the old definitions/report and schedule the cutover without concurrent reporting.

Release prerequisites:

- `COMMIT_TS` is guaranteed non-null by the source contract. Keep the existing sink schema and MAX-equality semantics; do not add a fallback timestamp or a redundant NULL filter.
- Supply complete emitted asset snapshots per RECID. The sink upserts `(RECID, ASSET_TYPE)` and does not retain all historical versions. A newer emitted batch hides older stored assets, but a version emitting no EXPLODED rows or a delete cannot advance the view's maximum. A late upsert can overwrite a newer row; the view cannot recover it.
- Complete both R18/R25 asset batches before comparing. One row arriving at a newer timestamp immediately advances the live view and temporarily hides the remaining older rows. Zero lag alone does not prove asset coverage, ordering, or equivalent business cutoffs; the report lock does not freeze either sink.
- Confirm `COMMIT_TS` identifies versions at the pipeline's effective timestamp precision, including Oracle `TIMESTAMP(3)`. Distinct versions sharing the stored timestamp are indistinguishable and all matching assets are retained.
- Validate Oracle object compilation, direct object privileges, dependencies, index definitions/statistics, actual plans and report capacity on the target environment. Reporting users need EXECUTE permission on the comparison procedure and SELECT permission on the DIFF snapshot table; latest-view inspection also needs SELECT on those views. Existing table/view grants are not interchangeable; verify reader permissions when migrating from the removed DIFF view.
- Validate registry schema `6226`, external parser/balance UDFs, Avro types, timestamp/time-zone handling and the intended `20261003` business cutoff. Local SQL adaptation cannot establish these runtime contracts.
- Review the existing embedded credentials, disabled database TLS DN matching, HTTP Schema Registry and message-inclusive error logging against the target environment's security policy. These settings are not validated or hardened by the latest-view cutover.

Local verification of the procedure-based workflow: actual report DDL, latest-view queries, procedure DELETE/INSERT SQL and diagnostic SELECTs were executed in isolated in-memory SQLite databases for DDAY and RHS1. The inline procedure produced the same 22 saved columns as the prior view-backed procedure for controlled fixtures covering tied latest assets, stale-asset exclusion, independent timestamps, individual/multiple balance mismatches, NULL equality versus NULL/zero, metadata-only differences, missing records/assets on both sides and signed deltas. COUNT and DIFF INSPECT remained on the stored result after upstream changes until refresh; repeated and empty refreshes and teardown also passed. Group-normalized reports matched, and the other ten repository artifacts were unchanged. SQLite adaptations covered Oracle DECODE, NULL concatenation, CREATE VIEW and index syntax, not Oracle compilation, PL/SQL execution/locks/rollback, financial precision, live ksqlDB/UDF/Avro or Kafka Connect. No Oracle SQL client or accessible local container runtime was available, so target-runtime and security release gates remain open.

## DDAY cutover

The DDAY cutover changes source topics to `DDAY_R18.FBNK_EB_C005` and `DDAY_R25.FBNK_EB_C005`, as well as all derived stream/topic names, connector names and Oracle object names. Configure the upstream publishers to supply these source topics, stop the old connectors, deploy the new stream/report scripts and DDAY connectors, then wait for the new sinks to catch up before comparing. Existing deployed objects, stored rows and connector offsets are not automatically renamed or migrated. Do not delete old deployed data until the new reconciliation is verified; replay requires the needed records to remain available in the new source topics.

## JDBC sink DLQ policy

Each EXPLODED connector uses the side-specific `<group>_<side>.SINK_ERROR` destination. Context headers identify the original topic/partition/offset, connector/task, failure stage and exception details. The DLQ retains the failed original key/value bytes, not an Oracle error table or a new business-record schema. Restrict topic/table/DLQ access because these records contain customer and balance data.

The baseline keeps `errors.tolerance=none`: failures are not silently skipped so reconciliation can continue with missing records. In upstream Kafka Connect error handling, a record may be reported to the DLQ before the tolerance check fails the task; a failed task therefore does not prove the DLQ is empty, and a configured DLQ does not guarantee delivery or continued processing. Validate the installed Kafka Connect/JDBC versions and actual task/DLQ state before relying on this behavior.

JDBC SQLExceptions use the configured max.retries/retry.backoff.ms before record-level isolation/reporting when an errant-record reporter is available. Table provisioning failures follow a separate reporting path; database connection acquisition failures can stop a task without sending records to the DLQ. ksqlDB parser/UDF failures occur upstream and are not captured by the sink DLQ.

The repository has no automatic DLQ consumer, repair or replay flow. Diagnose using the context headers and worker logs, repair the cause, recover/replay through the supported source-offset or targeted republish procedure, then verify sink coverage before rerunning reconciliation. Message-inclusive error logging intentionally remains enabled for diagnostics. A DLQ record is not proof of a committed skip or a successful recovery.

The configured DLQ replication factor applies when Connect creates a missing topic; it does not change an existing topic's replication.

References: [Confluent JDBC sink DLQ behavior](https://docs.confluent.io/kafka-connectors/jdbc/current/sink-connector/overview.html#dead-letter-queue) and [Kafka 3.9 error reporting/tolerance implementation](https://github.com/apache/kafka/blob/3.9/connect/runtime/src/main/java/org/apache/kafka/connect/runtime/errors/RetryWithToleranceOperator.java).

## Deployment verification boundaries

- Before rerunning stream scripts, identify and terminate their existing persistent ksqlDB queries using the target version's supported lifecycle commands. `DROP ... IF EXISTS` does not terminate running queries. Do not drop the shared schema streams while any group depends on them.
- Supply complete, controlled reconciliation snapshots or rebuild the sinks externally. The baseline pipeline upserts emitted assets but does not delete a stored asset when a later record removes it or produces no rows; forwarding `OP_TYPE` is not an Oracle delete operation.
- Verify stable Kafka keys/partition ordering for updates to the same `(RECID, ASSET_TYPE)`. JDBC upsert does not reject an older `COMMIT_TS`; multiple tasks do not establish global source-time ordering.
- Verify expected record/asset coverage and equivalent business cutoffs for R18/R25, not just zero connector lag. The report's exclusive lock protects its diff table, not synchronization of the two upstream sinks. Run the comparison procedure from a dedicated reporting session because its COMMIT also commits other work in that session.
- Validate actual UDF/Avro output types, registry schemas, timestamp/time-zone handling and Oracle field widths. Balances remain `NUMBER(38,4)` as in the baseline: more than four fractional digits are rounded, and more than 34 integer digits cannot fit. SQLite smoke does not verify this financial precision boundary.
- Message-inclusive worker error logging remains intentionally enabled for diagnosis. Restrict worker-log and DLQ access; with `errors.tolerance=none`, investigate failed tasks and verify coverage rather than assuming DLQ reporting allows continued processing.
- Verify execution plans and capacity on the target Oracle environment. `PARALLEL(8)` is a hint, not a guarantee of actual degree, and concurrently running reports can multiply resource demand.
