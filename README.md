# Reconciliation deployment

1. Run `F_STANDARD_SELECTION.sql` **once** to create the shared R18/R25 source and parsed streams for both DDAY and RHS. Its DROP statements recreate the parsed topics; do not rerun it between batches. The shared input topics are `R18.F_STANDARD_SELECTION` and `R25.F_STANDARD_SELECTION`.
2. Run `DDAY/R18_FBNK_EB_C005.sql` and `DDAY/R25_FBNK_EB_C005.sql` for DDAY. Run `DDAY/report.sql` to recreate the Oracle tables **before** deploying the matching connectors in `DDAY/`. The report script also calls the comparison procedure; run the procedure again once the sinks have caught up.
3. For each RHS batch under `RHS/RHS1/` through `RHS/RHS4/`, run its two stream SQL files (`R18_FBNK_EB_C005.sql` and `R25_FBNK_EB_C005.sql`), then its own `report.sql` **before** deploying the matching connectors. Each batch has separate Oracle sink tables, diff table, view and comparison procedure, named with its batch prefix (`RHS1` … `RHS4`). For example, RHS1 sinks into `CONFLUENT.RHS1_R18_FBNK_EB_C005_EXPLODED` and `CONFLUENT.RHS1_R25_FBNK_EB_C005_EXPLODED`; its report uses `CONFLUENT.RHS1_R18_R25_FBNK_EB_C005_DIFF` and `CONFLUENT.P_COMPARE_RHS1_R18_R25_FBNK_EB_C005`. There is no shared `RHS/report.sql`. Once that batch's sinks have caught up, call its comparison procedure again; do not rerun the whole report script, because it drops and recreates that batch's tables. Stop a batch's connectors before recreating its tables. Reports for other batches are not dropped or overwritten.
   - `RHS/RHS1/report.sql`
   - `RHS/RHS2/report.sql`
   - `RHS/RHS3/report.sql`
   - `RHS/RHS4/report.sql`

   When migrating existing deployments, stop the affected RHS connectors before changing `table.name.format`. Their identities and input topics are unchanged, so their committed offsets are retained: changing the destination alone does not backfill the new empty batch tables. Verify that the full required exploded input is still retained, then reset the stopped sink connector's offsets to the required starting position through the Kafka Connect version's supported offset-management interface, or deploy a fresh connector identity configured to start at the required earliest offsets. If retained input is incomplete, republish/recompute the complete required batch before consuming it. Resume only after the new tables exist; verify expected RECID/asset coverage on both sides as well as sink completion before comparing. Do not blindly copy old shared tables, which may contain mixed batches. Existing shared RHS tables and report objects are not migrated or deleted by the new scripts; retain them until any needed historical results have been archived.

All DDAY/RHS ksqlDB pipelines use schema ID `6226` for `EB_CONTRACT_BALANCES` in `PARSE_T24_RECORD`. Each derived stream projects `ROWKEY` to preserve the Kafka message key required by ksqlDB. `ROWKEY` is the message key, not a column in the Oracle sink tables; EXPLODED connectors use `RECID, ASSET_TYPE` and DEBUG connectors use `RECID` from the record value as their upsert primary key. Confirm the hard-coded `20261003` used by `EXPLODE_ASSET_BALANCES` matches the intended reconciliation date.

The report scripts DROP existing Oracle objects without an existence check; on first deployment, handle the expected missing-object errors or run only the CREATE section. Their final procedure invocation runs before the sinks have populated newly created tables. Each report compares only `OPEN_BAL`, `DR_MVT`, `CR_MVT`, `CLOSE_BAL` and row presence, not metadata fields.

All five reports use `/*+ PARALLEL(8) */` for the comparison SELECT and inspection queries. OPERATIONS contains the procedure invocation, followed by separate COUNT and INSPECT sections. Both sections order tables as EXPLODED (R18, R25), DEBUG (R18, R25), then DIFF. Each of the ten queries appears once for its intended table. EXPLODED/DEBUG COUNT queries include `INDEX_FFS(t)` specifying only the alias; all COUNT queries remain unfiltered and end on line 2. INSPECT queries place SELECT on line 1 and FROM on line 2. EXPLODED/DEBUG SELECT * queries include intentional comment template `--WHERE RECID = '';` on line 3 and `ORDER BY COMMIT_TS DESC` on line 4. The trailing semicolon in this commented template is intentional and must be preserved; it does not affect execution while commented. The DIFF SELECT has no WHERE template and keeps `ORDER BY RECID, ASSET_TYPE` on line 3. Standalone `/` delimiters remain omitted for DBeaver. Execute each complete `CREATE ... PROCEDURE ... END;` or `BEGIN ... END;` block as one statement/selection, not as separate internal statements. Oracle decides whether to honor the hints; verify actual execution plans in the target environment. Views, diff-table projections and procedure INSERT/SELECT blocks retain their multiline format, with one projection column per line. Independent statements are separated by one blank line. All SQL section headings use the stream convention: a title enclosed by two `-- ============================================================` lines, with one blank line before and after the heading block except at file start. KSQL preambles consistently use SET, then the run-once note, then section headings. Related timestamp aliases and RTRIM CASE expressions are vertically aligned; logical blocks use four-space indentation with aligned expression continuations.

The connectors contain database credentials as requested: restrict access to these files and rotate the password if it is exposed. The Oracle wallet must exist at the configured path on every Kafka Connect worker.

## QUICKCHECK and DDAY cutover

Every DDAY/RHS1-RHS4 stream script creates a side-specific `FBNK_EB_C005_QUICKCHECK` stream/topic. It retains `ROWKEY` and all five value fields declared by the first source stream (`RECID`, `OP_TYPE`, `OP_TS`, `CURRENT_TS`, `XMLRECORD`), with no value-field additions, renames or transformations, selecting exactly `XMLRECORD = '' OR XMLRECORD IS NULL`. The timestamp fields remain their original strings; fields present in the Kafka value but not declared in the source stream are not included. It is a diagnostic branch, not a filter on the main parsed/balance pipeline, and has no Oracle sink connector. For example, inspect `DDAY_R18_FBNK_EB_C005_QUICKCHECK` or `RHS1_R25_FBNK_EB_C005_QUICKCHECK` in ksqlDB. Stop the existing QUICKCHECK query before rebuilding the branch; its value schema changes from `COMMIT_TS`/`REPLICAT_TS` timestamps to `OP_TS`/`CURRENT_TS` strings, so account for the existing topic's Schema Registry compatibility policy during deployment.

The DDAY cutover changes source topics to `DDAY_R18.FBNK_EB_C005` and `DDAY_R25.FBNK_EB_C005`, as well as all derived stream/topic names, connector names and Oracle object names. Configure the upstream publishers to supply these source topics, stop the old connectors, deploy the new stream/report scripts and DDAY connectors, then wait for the new sinks to catch up before comparing. Existing deployed objects, stored rows and connector offsets are not automatically renamed or migrated. Do not delete old deployed data until the new reconciliation is verified; replay requires the needed records to remain available in the new source topics.

## Parsed DEBUG sinks

All ten DDAY/RHS1-RHS4 R18/R25 stream scripts create a `_DEBUG` branch directly from their `_PARSED` stream. For example, `RHS1_R18_FBNK_EB_C005_DEBUG` publishes to `RHS1_R18.FBNK_EB_C005_DEBUG` and sinks into `CONFLUENT.RHS1_R18_FBNK_EB_C005_DEBUG`. The balance/report pipelines are unchanged.

The DEBUG value contains `RECID`, `OP_TYPE`, `COMMIT_TS`, `REPLICAT_TS` and all eight fields declared in `schema.json`: `APPLICATION`, `CUSTOMER`, `DATE_LAST_UPDATE`, `CURR_ASSET_TYPE`, `OPEN_BALANCE`, `DEBIT_MVMT`, `CREDIT_MVMT`, `TYPE_SYSDATE`. Every parsed field has an explicit alias and remains an unmodified string, including multivalue/subvalue separators, leading zeros and decimal digits. Oracle stores all eight parsed fields as `VARCHAR2(4000)`. Values exceeding the Oracle column limit fail the sink rather than being truncated; BYTE/CHAR semantics depend on the DDL session's NLS_LENGTH_SEMANTICS. RECID remains VARCHAR2(255), OP_TYPE remains VARCHAR2(16), and timestamps remain TIMESTAMP(3). The tables contain only these twelve value columns, starting with RECID; there are no Kafka coordinate columns. `ROWKEY` remains the Kafka key, not an Oracle value column. Original XML and unparsed timestamp strings are not present in PARSED and are not added to DEBUG.

DEBUG deliberately has no `CURR_ASSET_TYPE IS NOT NULL` filter: it includes parsed records with missing assets or NULL DATA. It cannot capture records that fail before PARSED emits them, nor fields excluded by the live parser schema. Confirm registry schema 6226 matches the local eight-field schema; parser/UDF behavior remains an external prerequisite.

Each directory (`DDAY/`, `RHS/RHS1/` through `RHS/RHS4/`) defines both R18/R25 DEBUG tables in its normal `report.sql`, alongside EXPLODED. The script includes DROP TABLE ... CASCADE CONSTRAINTS PURGE, CREATE TABLE with RECID NOT NULL and PRIMARY KEY (RECID), and the same COUNT/SELECT inspection queries as EXPLODED. The primary key supplies the RECID lookup index. Rerunning report.sql recreates both DEBUG and EXPLODED sink tables; there is no separate debug.sql deployment step.

Each DEBUG connector matches its corresponding EXPLODED connector exactly except its name, input topic and destination table use DEBUG, and `pk.fields=RECID` instead of `RECID, ASSET_TYPE`. This includes `insert.mode=upsert`, `pk.mode=record_value`, `auto.create=true`, `auto.evolve=false` and the shared side-specific `<group>_<side>.SINK_ERROR` DLQ. DEBUG tables retain one row per RECID: the last applied event overwrites the previous value; they do not retain event history or reject older COMMIT_TS values. Replay of the same value does not add rows. NULL RECID fails the primary-key contract. Run report.sql before starting the connectors to ensure the explicit column widths.

Deploy DEBUG through the same lifecycle as EXPLODED: stop the affected connectors and persistent stream queries before rebuilding, run the group's two stream scripts and report.sql, then deploy/resume the matching EXPLODED and DEBUG connectors. Recreating sink tables does not reset committed connector offsets; replay retained input using the supported offset-management interface or fresh connector identities to repopulate both sinks. Earliest cannot restore expired/compacted records. After the sinks catch up, call the comparison procedure again instead of rerunning report.sql. Apply the same backup/data-loss precautions to both sink types.

To preserve every emitted event until sinking, verify DEBUG topics use non-compacted retention and adequate retention/worker capacity. Recomputing/replaying input can overwrite the current RECID snapshot, including with an older event. The RHS retention script includes DEBUG and the shared sink DLQ, reducing the replay window to one day; Oracle rows do not expire with Kafka retention. Restrict topic/table/DLQ access because these records contain customer and balance data.

Local verification: all ten DEBUG connectors matched their corresponding EXPLODED configuration after changing only DEBUG identity fields and the RECID key. SQLite-adapted upsert smoke verified replacement of a RECID value, replay without duplicate rows, NULL-key rejection and unchanged twelve-column layouts. Integrated report lifecycle smoke verified both DEBUG tables in all five reports: DROP/CREATE clears old rows, COUNT/SELECT inspection queries execute, and the schemas and existing report logic remain unchanged. This is not live ksqlDB/UDF, Avro, Kafka Connect or Oracle validation, and SQLite does not enforce Oracle VARCHAR2 width semantics. Before rollout, verify actual schema/string types, TIMESTAMP mapping and Oracle VARCHAR2 binding/length boundaries with the deployed versions. No Oracle or ksqlDB SQL client was available locally.

## RHS1-RHS4 topic retention

Run `bash RHS/set-retention-1d.sh` from the repository root on a host with network access to `10.35.222.247:9092` and the Kafka CLI tools on PATH. The script supports both `kafka-topics`/`kafka-configs` and their `.sh` variants, using the unauthenticated PLAINTEXT listener.

The eight RHS stream scripts declare 48 topics: source, QUICKCHECK, PARSED, DEBUG, MAPPED and EXPLODED for each RHS1-RHS4/R18-R25 pair. The sixteen EXPLODED/DEBUG connector configurations share side-specific `RHSn_Rxx.SINK_ERROR` DLQ topics. The script selects existing topics from the broker with the case-sensitive prefix expression `^RHS[1-4]([^0-9]|$)`, so it includes existing DLQs and any additional topics under those prefixes, but excludes RHS10/RHS20 and other numbered groups. It does not select DDAY, TEST, the shared `R18`/`R25.F_STANDARD_SELECTION` topics or conventionally named Kafka/Connect/ksqlDB internal topics.

The script prints the selected topics, reads all their current overrides before making changes, sets only `retention.ms=86400000` (one day), then reads back and verifies each update. It creates no topics and changes neither broker defaults nor `cleanup.policy`. Updates are sequential, not atomic: a command or verification failure stops the script, but earlier successful updates remain applied. A stream/topic recreation can lose the override; rerun the script after recreation if the same policy is still required.

Before running, ensure the reconciliation pipeline has consumed the needed records and no longer needs the older replay window. When `cleanup.policy` contains `delete`, expired segments can be deleted asynchronously; increasing retention cannot restore deleted data. Pure `compact` topics do not expire after one day solely because `retention.ms` is set.

## Deployment verification boundaries

- Before rerunning stream scripts, identify and terminate their existing persistent ksqlDB queries using the target version's supported lifecycle commands. `DROP ... IF EXISTS` does not terminate running queries. Do not drop the shared schema streams while any group depends on them.
- Supply complete, controlled reconciliation snapshots or rebuild the sinks externally. The baseline pipeline upserts emitted assets but does not delete a stored asset when a later record removes it or produces no rows; forwarding `OP_TYPE` is not an Oracle delete operation. QUICKCHECK does not quarantine records from the main parser.
- Verify stable Kafka keys/partition ordering for updates to the same `(RECID, ASSET_TYPE)`. JDBC upsert does not reject an older `COMMIT_TS`; multiple tasks do not establish global source-time ordering.
- Verify expected record/asset coverage and equivalent business cutoffs for R18/R25, not just zero connector lag. The report's exclusive lock protects its diff table, not synchronization of the two upstream sinks. Run the comparison procedure from a dedicated reporting session because its COMMIT also commits other work in that session.
- Validate actual UDF/Avro output types, registry schemas, timestamp/time-zone handling and Oracle field widths. Balances remain `NUMBER(38,4)` as in the baseline: more than four fractional digits are rounded, and more than 34 integer digits cannot fit. SQLite smoke does not verify this financial precision boundary.
- Restrict worker logs and DLQ access: `errors.log.include.messages=true` can expose record data including CUSTOMER. With `errors.tolerance=none`, task errors must be investigated; a configured DLQ is not proof that processing continues.
- Verify execution plans and capacity on the target Oracle environment. `PARALLEL(8)` is a hint, not a guarantee of actual degree, and concurrently running reports can multiply resource demand.
